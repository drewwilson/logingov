Storage layer decision

PlanetScale vs Cloudflare D1

Both are viable MySQL-compatible options for this stack. This page lays out the trade-offs, our recommendation, and the multi-region failover strategy that makes the choice work in production.

Recommendation — PlanetScale
For an auth system processing millions of logins per day with strict consistency requirements, PlanetScale's multi-region primary + read replicas give you better operational control and proven write throughput than D1's current single-primary architecture. D1 is the simpler path but has meaningful constraints at scale. The cost difference is justified by the operational guarantees.

Multi-region failover strategy

An auth system failing is effectively a government-wide outage. The failover architecture needs to be designed from the start, not bolted on later. With PlanetScale, we get real primitives to build on.

Strategy 01
Read replicas in every target region
Deploy PlanetScale read replicas in US-East, US-West, EU-West, and AP-SE. Cloudflare Hyperdrive routes each Worker's read queries to the nearest replica automatically — sub-5ms reads regardless of where the auth request originates. The primary only handles writes.
~2ms p99 reads
Strategy 02
Hot standby primary with automatic promotion
Configure a standby primary in a second US region (US-West). PlanetScale's Vitess topology manager automatically promotes the standby to primary if the active primary fails, with no manual intervention required. Workers using Hyperdrive automatically reconnect to the new primary endpoint.
~30s RTO
Strategy 03
Read-only degraded mode during failover
During the ~30 second primary failover window, the auth Workers fall back to a read-only degraded mode: existing sessions continue to work (DO + KV), token validation works (KV/DO), but new logins and registrations are queued or returned a retryable 503. Queued requests are replayed via CF Queues once the new primary is healthy.
503 with Retry-After
Strategy 04
Auth hot path bypasses the database entirely
Token validation, session checks, and JWKS lookups never hit PlanetScale — they resolve entirely from Durable Objects and KV. Only login, registration, and account mutations require a database write. This means a DB outage affects only the write path, not the vast majority of traffic.
~85% of traffic unaffected
Strategy 05
Vitess sharding for auth_codes and events
The two highest-write tables — auth_codes and identity_events — are sharded on user_id. This distributes write load across shards and prevents hot-row contention during traffic spikes (e.g., a high-volume agency onboarding millions of users).
horizontal scale
Strategy 06
Point-in-time restore + audit log redundancy
PlanetScale retains 7-day PITR. The identity_events audit table is also streamed to Cloudflare R2 in real-time via a Queue consumer Worker (JSON Lines format). In a catastrophic DB loss, the audit log in R2 serves as a complete reconstruction source and FedRAMP-compliant archive.
7-day PITR + R2 archive
RTO / RPO targets
With this architecture: read path RTO = 0 (replicas are always available independently of primary), write path RTO ≈ 30 seconds (automatic Vitess primary promotion), RPO ≈ 0 (synchronous replication to standby before acknowledging writes). The 30-second write outage window is covered by the degraded-mode queue strategy above.
The case for D1 in early-stage development
D1 is genuinely the right choice before you hit production scale. Zero configuration, single vendor, and local dev parity with wrangler dev make the early build phase faster. The recommendation is to start with D1 for the first 6 months, then migrate to PlanetScale when write throughput or multi-region failover become requirements. The schema design is identical — migration is a data port, not a rewrite.
03

D1 → PlanetScale migration path

1
Schema parity
D1 (SQLite) and PlanetScale (MySQL 8.0) share nearly identical DDL for this schema. The main changes: TEXT → VARCHAR/TEXT, DATETIME → DATETIME(6) for microsecond precision, and dropping any AUTOINCREMENT in favor of UUID v7 primary keys. Write and validate the MySQL DDL against a PlanetScale branch before touching production.
2
Deploy PlanetScale alongside D1
Stand up PlanetScale with the full schema. Configure Hyperdrive in wrangler.toml. Dual-write all mutations (login, registration, account changes) to both D1 and PlanetScale for a shadow period of 48–72 hours. Use a feature flag in KV to control which store is authoritative for reads.
3
Backfill historical data
Export all D1 tables to CSV via wrangler d1 export. Transform and import into PlanetScale using LOAD DATA INFILE or the PlanetScale import tool. Verify row counts and checksums per table. The identity_events table is append-only so backfill is safe at any time.
4
Cut over reads
Flip the KV feature flag to route reads to PlanetScale. Monitor error rates and latency for 24 hours. The dual-write is still active so rollback is instant — flip the flag back to D1 reads if anything looks wrong. No data loss possible during this phase.
5
Cut over writes, retire D1
Remove D1 dual-write code. Remove the D1 binding from wrangler.toml. Keep the D1 database in read-only archival mode for 30 days, then delete. PlanetScale is now the sole source of truth. Enable Vitess sharding for auth_codes and identity_events via a PlanetScale deploy request.
