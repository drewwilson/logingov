01

Auth hot path — zero DB reads

Critical path optimization
Token validation (GET /userinfo, OAuth2 introspection) only touches KV (JWKS lookup) and a Durable Object (session check). PlanetScale is never read on the happy path — only on login, registration, and account changes. Better Auth's session layer uses Cloudflare KV as secondary storage so active sessions are always local to the Worker.
Step 1 — WAF + GeoDNS
Request hits Cloudflare edge. WAF rules apply. Routed to nearest PoP. For /authorize, PKCE or JWT client auth is validated immediately in the Worker.
Step 2 — Durable Object session
Auth state lives in a DO. PKCE challenge, nonce, requested scopes, IAL/AAL target stored atomically. DO runs in the same region as the user's request.
Step 3 — Token issuance
On code exchange, Better Auth resolves the auth code from PlanetScale (single-use enforced via transaction, routed via Hyperdrive). RS256 id_token signed with jose. Access token written to KV with TTL.
Step 4 — Userinfo
Bearer token validated against KV. User attributes fetched from PlanetScale nearest read replica via Hyperdrive. Claims scoped to SP's requested scopes. Pairwise sub computed in-memory via Better Auth's custom claims hook.
Step 5 — Logout
Better Auth invalidates the session (DO alarm cancelled + KV cleared). id_token_hint validated. Post-logout redirect URI checked against PlanetScale SP config. RISC session-revoked queued.
Error + fraud paths
Inbound RISC SETs handled by a Queue consumer Worker — fraud signals trigger Better Auth session invalidation + PlanetScale flag asynchronously, without blocking the hot path.
02

PlanetScale schema — key tables

Design principles
All PII fields (ssn, birthdate, address, phone) are encrypted at the application layer with AES-256-GCM before writing to PlanetScale — separate from at-rest encryption. Better Auth generates the core schema (user, session, passkey, twoFactor) via npx auth generate; login.gov-specific tables are defined alongside in Drizzle. Referential integrity is enforced in Worker transactions rather than FK constraints (Vitess limitation). Audit log rows are append-only by policy and never updated or deleted.
